# Issue tracker: GitHub Issues

`/emet` talks to GitHub Issues in jobship via the `gh` CLI — never the
GitHub MCP server. Every operation below is a literal `gh` invocation; there is
no adapter layer to keep in sync with `gh`'s own flags.

## Ticket shape

- Ticket id: the bare issue number (`^JOB-\d+$`, e.g. `JOB-1`).
- Spec: a parent issue. Create tickets as its sub-issues:
  `gh issue create --title "..." --body "..." --parent <spec-number>` (`gh`
  ≥2.100 has native `--parent`/`--blocked-by`/`--blocking`; check
  `gh --version` if this repo pins an older release).
- Frontier: `gh issue view <spec-number> --json subIssues` returns the full
  child set in one call — filter to open, unblocked (`blockedBy` empty or
  every blocker already closed).
- Read a ticket: `gh issue view <number> --json title,body,labels,state,blockedBy,blocking`.
- Comment: `gh issue comment <number> --body "..."` /
  `gh issue view <number> --json comments`.
- Blocking relations: `gh issue edit <number> --add-blocked-by <other>` /
  `--add-blocking <other>` (native, not a text convention).

## Priority and workflow-state substitutes

GitHub Issues has no native priority field or workflow states. This repo uses
label maps instead (`tracker.github` in `emet.config.json`):

- `priorityLabels`: empty. Tickets are ordered by `createdAt` ascending only; wave order comes from
  the dependency layers, not from priority.

Deliberately **not** using GitHub Projects v2 Status fields here: they need
`gh auth refresh -s project`, a board per repo, and GraphQL — too much setup
for a repo that just wants `/emet` to work.

## Who writes state transitions

`tracker.transitions`: `onStart: worker` (apply the `status:in-progress` label
on its own ticket), `onPrOpen: coordinator` (apply `status:in-review` when
opening the wave's PR), `onPrMerge: coordinator` — wave PRs target `develop`,
not the default branch `main`, so a `Closes #N` line in the PR body does not
close anything. After the merge the coordinator closes each ticket itself:
`gh issue close <number> --reason completed`.

## Spec and ticket blocks

- Spec body: `## Specs` (`- **S1**: …`, one per line), then
  `## Global Constraints` (rules every worker and reviewer must obey; copied verbatim
  into each brief) and `## Review Focus` (inputs the spec implies but nothing
  tests; each gets a test).
- Ticket body: `Covers: S…` under the title, then `## Interfaces`
  (`Consumes:` / `Produces:` with signatures), `## Project skills`,
  `## Allowed edit surfaces`, `## Context budget`.
- Every S# needs an acceptance scenario (`Scenario: WHEN … THEN …`); `emet
  validate` enforces coverage, scenarios, disjoint wave surfaces and acyclic
  blockers before approval.

## External surface

Private repository, no outside contributors for now.
